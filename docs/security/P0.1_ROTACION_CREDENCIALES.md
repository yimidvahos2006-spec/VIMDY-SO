# P0.1 — Rotación de credenciales expuestas

**Proyecto:** VIMDY OS  
**Prioridad:** P0 — seguridad  
**Estado:** `BLOCKED_EXTERNAL` — el repositorio puede sanearse localmente, pero la revocación real exige acceso autenticado a los proveedores.  
**Regla:** no copiar valores de credenciales a este documento, Git, chats, issues, logs ni capturas.

## Alcance de la contención

El ZIP original incluía archivos de entorno y metadatos locales. Se deben considerar potencialmente comprometidas las credenciales reales que aparecían en esos archivos, aunque después se haya creado una copia saneada. Eliminar un archivo del ZIP o del repositorio no revoca una credencial.

Servicios/valores a revisar, sin divulgar sus valores:

- Token de acceso/despliegue de Vercel.
- Clave de servidor de Supabase (`SUPABASE_SERVICE_ROLE_KEY`) o cualquier nueva clave secreta de Supabase.
- Clave API de Resend y contraseña SMTP. En la integración SMTP de Resend, la contraseña es una API key.
- Secreto OAuth de Google, únicamente si se encontraba configurado con un valor real en los archivos expuestos.
- Cualquier otra clave de proveedor que se confirme en los archivos originales, CI, logs o respaldos.

## Procedimiento obligatorio

### 1. Vercel

- [ ] Entrar al panel de Vercel con la cuenta propietaria.
- [ ] En la configuración de la cuenta, abrir **Tokens** y revocar el token incluido en los archivos expuestos.
- [ ] Revisar actividad y notificaciones de uso no reconocido.
- [ ] Crear un token nuevo solo si hace falta, con alcance mínimo, caducidad y equipo/proyecto correctos.
- [ ] Actualizar el secreto en los entornos de CI/CD autorizados; nunca guardarlo en el repositorio.
- [ ] Ejecutar una nueva implementación y comprobar que no depende del token revocado.

Documentación oficial: https://vercel.com/docs/rest-api

### 2. Supabase

- [ ] Abrir **Project Settings → API Keys** del proyecto correcto.
- [ ] Si se expuso la clave legacy `service_role`, crear una nueva secret key y sustituir primero la antigua en cada backend, Edge Function, job y entorno CI que la use.
- [ ] Confirmar que las llamadas de servidor funcionan con la nueva clave.
- [ ] Desactivar la clave legacy comprometida (o eliminar la nueva secret key comprometida) solo después de comprobar que ya no hay componentes dependientes de ella.
- [ ] Revisar que ninguna clave con privilegios elevados esté asignada a variables `VITE_*`, código frontend o archivos incluidos en `dist/`.
- [ ] No regenerar a ciegas el secreto de firma JWT: puede invalidar tokens/credenciales existentes y causar una caída. Seguir la guía de rotación que corresponda al tipo de clave del proyecto.

Documentación oficial:
- https://supabase.com/docs/guides/getting-started/api-keys
- https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys
- https://supabase.com/docs/guides/troubleshooting/rotating-anon-service-and-jwt-secrets-1Jq6yd

### 3. Resend / SMTP

- [ ] En Resend, revocar la API key expuesta.
- [ ] Crear una nueva API key con permisos mínimos necesarios (preferiblemente solo envío y restringida al dominio correcto).
- [ ] Actualizar `RESEND_API_KEY` y, si SMTP usa esa misma credencial, actualizar `RESEND_SMTP_PASS` en el almacén de secretos del entorno correspondiente.
- [ ] Ejecutar una prueba de correo en un entorno de prueba y confirmar entrega/registro.
- [ ] Confirmar que el token anterior ya no funciona sin escribirlo en terminal ni en logs.

Documentación oficial: https://resend.com/changelog/smtp-service

### 4. OAuth de Google y otras credenciales

- [ ] Confirmar si el secreto de cliente OAuth era real y estaba expuesto.
- [ ] Si lo era, regenerarlo en Google Cloud Console y actualizar solo el backend/configuración de Auth que corresponda.
- [ ] Revisar otros proveedores y credenciales presentes en los archivos originales; revocar cualquier valor real que haya quedado expuesto.

### 5. Buscar copias adicionales

- [ ] Revisar historial Git (ramas, tags y commits), artefactos CI, logs, respaldos, archivos compartidos y paquetes publicados.
- [ ] Buscar los tipos de secretos por nombre y/o con un escáner de secretos que oculte los valores en sus resultados.
- [ ] Revocar primero; reescribir el historial por sí solo no vuelve segura una clave expuesta.
- [ ] No pegar ni adjuntar los valores encontrados al informe. Registrar solo proveedor, identificador no secreto, fecha y estado de revocación.

## Verificación de cierre

La tarea solo puede marcarse `PASS` cuando se haya comprobado todo lo siguiente:

- [ ] Las credenciales anteriores están revocadas o desactivadas.
- [ ] Los componentes usan las credenciales nuevas desde un almacén seguro.
- [ ] Las funciones críticas dependientes de esas credenciales pasaron pruebas con la nueva configuración.
- [ ] No hay secretos privilegiados en `VITE_*`, bundles del navegador, `.env.example` ni el paquete de release.
- [ ] Se revisaron los lugares donde pudieron quedar copias adicionales.
- [ ] Se registró evidencia sin incluir valores secretos.
